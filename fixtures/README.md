# Fixtures

Recorded sessions in the `junk trace v1` format (`crates/junk-trace`), used by the replay tests
and by `junk replay` and `junk sony replay`. Each file's header repeats what is said here.
Raw captures (`.pklg`) are not published; the traces are the record.

| File | Device | Real or synthetic | How it was produced | Made up or redacted |
|---|---|---|---|---|
| `colmi-r10/qring-sync-2026-07-02.trace` | Colmi R10_F300, firmware RT03CR_1.00.02_260319 | Real, with reconstructed parts | One sync session, taken from the QRing 1.2.9 app's own packet log on macOS (no PacketLogger capture exists). The channel of each line is inferred from the frame shape. | The 16 big-data replies (`bc 27` sleep, `bc 2a` SpO2, `bc 25` temperature) were logged by the app as headers only, so their bodies are **reconstructed** from the app's own database rows for that day and the layouts in `docs/colmi-protocol.md`; each reconstructed frame's CRC matches one the log recorded. The peripheral identifier in the `!` event lines is a made-up UUID. |
| `colmi-r10/thering-realtime-2025-11-19.trace` | Colmi R10_F300 | Real | A PacketLogger capture of a live heart-rate workout (the `0x77`/`0x78` stream, then the `bc 41`-`45` record fetch) made while another phone app drove the ring, converted with `tools/pklg2trace.py` (command below). The `.pklg` is not published. | No Bluetooth addresses are kept: only ATT traffic on the ring's known characteristics survives the conversion. |
| `colmi-r10/junk-sync-2026-09-06.trace` | Colmi R10_F300 | Real | Recorded by this stack: `junk sync --record`, a seven-day sync. Nothing elided or inferred. | Nothing; the trace holds no addresses or names beyond the model. |
| `colmi-r10/junk-live-2026-09-06.trace` | Colmi R10_F300 | Real | Recorded by this stack: `junk live --record`, a 75 s workout with its stored record. Nothing elided or inferred. | Nothing; same as above. |
| `soundcore-motion-300/probe-2026-09-15.trace` | Soundcore Motion 300 | Real | `cargo run -p junk-rfcomm --example probe` against a paired speaker: one request and one reply over RFCOMM, the capture that settled the packet header. | The reply carries the speaker's serial number; it was replaced with a placeholder (`ACCLXX0000000000x`, in the reply bytes and the header). The trace holds no Bluetooth address. |
| `sony-wh1000xm4/synthetic-init-status.trace` | Sony WH-1000XM4 (as a fake) | **Synthetic**: never on a wire | Generated by `crates/junk-sony/tests/proto.rs` (`synthetic_trace`); regenerate with `JUNK_SONY_REGEN=1 cargo test -p junk-sony --test proto synthetic`. | Everything: the replies, the function list, the capabilities, the values and the timestamps are made up to exercise the driver. They are not an XM4's. |

The timestamps in a PacketLogger conversion are the capturing machine's wall-clock time as if it
were UTC; `--tz` names the zone the capture was taken in.

How the live-HR trace was converted:

```sh
uv run tools/pklg2trace.py --tz America/New_York --desc "Colmi R10_F300 live HR session (0x77/0x78 workout stream, then bc41-45 workout record fetch), captured with PacketLogger from the thering app, 2025-11-19 10:20 America/New_York" thering-realtime-2025-11-19.pklg -o fixtures/colmi-r10/thering-realtime-2025-11-19.trace
```

`tools/pklg2trace.py` and its tests need [uv](https://docs.astral.sh/uv/):
`uv run --with pytest pytest tools`.

## Adding a fixture

Say which device and firmware, how it was produced, and what was made up or redacted, in the
file's header and in this table. A trace must never contain real Bluetooth addresses, serial
numbers, other people's health data or personal identifiers. A fixture that was not captured
from a device must say so in its file name and header.
